# Evaluation Strategy — AI Revenue Recovery Platform

---

## Purpose

Evaluation is a first-class concern for this platform. The goal is to demonstrate, with real measurable evidence, that the AI-assisted recovery workflow produces meaningful outcomes — and to understand precisely where it succeeds, where it fails, and where it makes incorrect decisions.

All metrics are computed from actual records. No numbers are hardcoded or estimated.

---

## Synthetic Dataset Strategy

### Why Synthetic Data

- Razorpay Test Mode provides payment infrastructure but not pre-built failure scenarios
- A curated synthetic dataset allows systematic evaluation across edge cases and failure types
- Synthetic data can be created to cover the full range of failure categories and intervention types
- It allows evaluation of stopping rules, escalation logic, and incorrect interventions in a controlled way

### Dataset Size

The target evaluation dataset is **100–500 synthetic payment/recovery records**.

This is large enough to compute statistically meaningful metrics while remaining small enough to be manually inspectable and verifiable.

### Dataset Structure

Each synthetic record represents one payment failure and its complete recovery lifecycle. A record includes:

- A simulated payment failure (failure reason, amount, currency, timestamp)
- A simulated customer profile (payment history, subscription status)
- A ground-truth label for the appropriate recovery action
- A ground-truth expected outcome (RECOVERED / FAILED / ESCALATED / STOPPED)

Ground-truth labels are assigned manually based on business rules — not generated by the AI. They represent what a reasonable human expert would decide.

### Failure Category Distribution

The dataset should intentionally cover:

| Failure Category | Approximate proportion |
|-----------------|----------------------|
| `INSUFFICIENT_FUNDS` | ~30% |
| `CARD_EXPIRED` | ~20% |
| `BANK_DECLINED` | ~20% |
| `NETWORK_ERROR` | ~10% |
| `PAYMENT_METHOD_INVALID` | ~10% |
| `CUSTOMER_INITIATED_FAILURE` | ~5% |
| `UNKNOWN` | ~5% |

Proportions are approximate starting points and may be adjusted based on what provides the most useful evaluation signal.

### Special Cases to Include

The dataset must include records that exercise:
- Retry limit exhaustion
- Recovery window expiry
- Repeated failure escalation
- High-value payment escalation
- Stopping rule triggers
- AI failure fallback (simulated by providing ambiguous/conflicting signals)
- Cases where the correct action is `STOP_RECOVERY`
- Cases where multiple plausible actions exist

## Evaluation Metrics

All metrics are computed from actual database records at evaluation time.

### Primary Recovery Metrics

| Metric | Definition |
|--------|-----------|
| Total revenue at risk | Sum of `amount_paise` across all recovery cases in the evaluation batch |
| Total revenue recovered | Sum of `recovered_amount_paise` from `RecoveryResult` records with status `RECOVERED` |
| Overall recovery rate | Total revenue recovered / Total revenue at risk |
| Number of payments analyzed | Count of recovery cases processed |
| Successful recoveries | Count of cases with result `RECOVERED` |
| Failed recoveries | Count of cases with result `FAILED` |
| Escalated cases | Count of cases with result `ESCALATED` |
| Stopped cases | Count of cases with result `STOPPED` |
| Unresolved / pending cases | Count of cases still in `PENDING_RESULT` state |
| Average recovery amount | Mean `recovered_amount_paise` across successful recoveries |

### AI Performance Metrics

| Metric | Definition |
|--------|-----------|
| AI intervention distribution | Count of each `recommended_action` type across the batch |
| Correct interventions | Cases where AI recommendation matched ground-truth label |
| Incorrect interventions | Cases where AI recommendation did not match ground-truth label |
| Incorrect intervention rate | Incorrect / Total |
| False-positive escalations | Cases escalated that would have been recoverable without escalation |
| Missed escalations | Cases not escalated that should have been (based on ground truth) |
| AI confidence distribution | Count of LOW / MEDIUM / HIGH confidence recommendations |
| AI failure rate | Count of cases where AI engine failed and fallback was applied |

### Guardrail Metrics

| Metric | Definition |
|--------|-----------|
| Guardrail APPROVED count | Recommendations approved by policy engine |
| Guardrail REJECTED count | Recommendations rejected by policy engine |
| Guardrail ESCALATED count | Recommendations escalated by policy engine |
| Stopping rules triggered | Count of cases where a stopping rule was applied |
| Retry limit triggers | Count of cases where retry limit guardrail fired |
| Recovery window expiries | Count of cases closed due to window expiry |

### Breakdown Metrics

Where applicable, metrics should be broken down by:
- Failure category
- Action type
- AI confidence level
- Payment amount range (small / medium / large)

## Held-Out Evaluation Concept

The synthetic dataset will be split into:

- **Development set (~70%):** Used during development to tune prompts, guardrail thresholds, and workflow logic
- **Held-out test set (~30%):** Reserved for final evaluation; not used during development

This separation ensures that evaluation results reflect genuine generalization rather than overfitting to development cases.

For the MVP buildathon demonstration, the held-out set provides the primary evaluation numbers.

---

## Recovery Measurement

Recovery measurement requires an actual payment outcome — not an inference. A case is only counted as `RECOVERED` when:

1. A `RecoveryAction` was executed successfully
2. A subsequent payment succeeded (confirmed via Razorpay webhook or API poll)
3. The successful payment amount is recorded in `RecoveryResult.recovered_amount_paise`

The recovered amount may differ from the original failed amount (e.g., partial payment). Both values are recorded separately.

---

## Incorrect Intervention Analysis

The evaluation must identify and document cases where the AI recommended the wrong action. For each incorrect intervention:

- Record the failure category
- Record the AI recommendation
- Record the ground-truth label
- Record the outcome (what actually happened with the wrong intervention)
- Identify whether the guardrail layer caught the error (rejected or escalated) or passed it through

This analysis should inform prompt improvements and guardrail refinements.

---

## Failure Case Evaluation

The evaluation must explicitly cover failure modes:

| Failure Mode | What to measure |
|-------------|----------------|
| AI engine failure | Was fallback applied? Was case audited correctly? |
| Razorpay API error during action | Was error handled gracefully? Was case flagged? |
| Recovery window expired before action | Was case closed correctly? |
| Retry limit exceeded | Did stopping rule trigger as expected? |
| Human approval not received | Was case left in appropriate state? |

---

## Stopping Rule Evaluation

For cases where a stopping rule should apply, the evaluation checks:

1. Did the guardrail trigger the stopping rule?
2. Was `STOP_RECOVERY` executed as the final action?
3. Was the case correctly closed?
4. Was the audit trail complete?

Stopping rules that fail to trigger on appropriate cases are a significant system defect.

---

## Reporting Format

At evaluation time, the platform will produce an evaluation report containing:

1. Summary metrics table (primary recovery metrics)
2. AI intervention distribution chart/table
3. Guardrail decision distribution
4. Incorrect intervention analysis (case-by-case where incorrect)
5. Failure case handling results
6. Stopping rule effectiveness
7. Recovery breakdown by failure category

The report is generated from actual database records — not assembled manually.

---

## What Evaluation Does Not Claim

- Evaluation results from Test Mode / synthetic data do not predict production performance
- Synthetic dataset results reflect curated scenarios, not a random sample of real business failures
- Recovery rates from the evaluation set should not be quoted as expected production recovery rates
- The evaluation demonstrates correct system behavior and reasonable AI decision quality, not commercial viability

These disclaimers should accompany any public presentation of evaluation results.
